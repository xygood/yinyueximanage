# 教学日历「小组排课时间」加载方案分析

## 一、当前方案简述

**目标**：用户在教学日历选择「教师 → 课程 → 班级 → 小组」后，红框内「排课时间」应直接显示该小组在排课结果中的时间（如「第1-2、4-17周周四第3节」），而不是「未查到排课记录」。

**实现要点**：
- 前端：小组选项来自 `scheduleService.getAll` 的排课列表，按 `group_id` 聚合出每个小组的 `studentIds`；选小组后把 `group_student_ids`（逗号分隔学号）传给日历接口。
- 后端：在 `_build_calendar_entries` 中依次尝试：
  1. **主查询**：课程（同课多行的 id + 课程编号）+ `group_id` 或 `student_id in group_student_ids`，且**有学号时不按班级过滤**。
  2. **course_code 回退**：仅按 `course_code` + group/学号再查一次；有学号时同样不按班级过滤。
  3. **直接回退**：仅按 `student_id in group_student_ids` + 课程（id 或 course_code），不做 group_id、班级等任何其它条件。

排课时间展示：用 `_format_schedule_time_summary(schedules, for_group=True)` 从查到的记录直接拼字符串，无额外计算。

---

## 二、当前方案的优劣

### 优点

| 点 | 说明 |
|----|------|
| **语义正确** | 有学号时不再用班级过滤，学号已唯一确定小组，避免 class_id / major_class 格式不一致导致漏查。 |
| **直接读取** | 最后一层「直接回退」就是按「学号 + 课程」从 `scheduled_classes` 读，和排课结果表一一对应，没有复杂业务计算。 |
| **兼容旧数据** | 同课多行（多班）、仅存 course_code 的老数据、group_id 缺失或不一致时，仍能通过 course_code 回退或学号+课程查到。 |
| **数据源一致** | 小组的 `studentIds` 来自同一套排课接口（`getAll`），与排课结果页同源，学号一致。 |

### 缺点

| 点 | 说明 |
|----|------|
| **多层回退，逻辑重** | 主查询 + 两重 fallback，代码路径多，排查「为什么走的是哪一层」时要顺着三条分支看。 |
| **可能多次查库** | 最坏情况会执行 3 次查询（主查、course_code 回退、直接回退），虽然多数情况第一次就命中。 |
| **依赖前端传学号** | 若小组选项未带 `studentIds`（例如来自别处或构造错误），后端只能靠 group_id/班级，可能再次落入班级格式问题。 |
| **课程匹配重复建设** | `course_ids_for_schedule` 与「同课多行」的构造在多处复用，若以后课程匹配规则变化要改多处。 |

---

## 三、是否有更好的方案？

下面几种替代思路，在「简单性 / 可维护性 / 兼容性」上各有取舍。

### 方案 A：小组课只做「学号 + 课程」单次查询（极简）

**做法**：当请求带 `group_student_ids` 时，**不再**先按 group_id + 班级做主查询，而是直接做当前「直接回退」那一层：  
`ScheduledClass` 满足 `student_id in group_student_ids` 且 课程为当前课（同课 id 或 course_code）。

**优点**：
- 逻辑极简：一条查询、一种语义，和「按学号从排课结果读」完全一致。
- 易维护、易测试，不会出现「主查询把结果滤掉、再靠回退救回」的隐蔽问题。

**缺点**：
- 完全不用 group_id，若历史数据里同一批学号对应多个 group_id（极少见），无法区分；当前业务下一门课一组学号即一组，一般可接受。
- 不再用 course_code 单独回退，若某条排课只有 course_code、没有 course_id，且 course_id 不在「同课 id 列表」里，理论上有漏查可能；实际同课 id 列表已包含按课程编号查到的 id，一般能覆盖。

**结论**：若可以接受「小组课只认学号+课程」的约定，这是更简单、更稳的方案，推荐作为后续简化方向。

---

### 方案 B：独立接口「按小组学号查排课时间」

**做法**：新增接口，例如  
`GET /api/teaching-calendar/group-schedule?course_id=xxx&group_student_ids=id1,id2,id3,id4`  
只做一件事：按 course_id（或 course_code）+ `group_student_ids` 查 `ScheduledClass`，返回格式化后的排课时间。

**优点**：
- 职责单一，合同清晰，便于单独测试、缓存或复用到其他页面。
- 教学日历在「已选小组」时只调这个接口，不再依赖整份日历大接口里的复杂分支。

**缺点**：
- 多一个接口与一次请求；若仍需要整份日历（周历、禁排等），还是要调原日历接口，可能变成「日历 + 小组排课时间」两次请求，需要前端配合。

**结论**：适合希望「小组排课时间」与「整份教学日历」解耦、或计划在其他地方复用「按学号查排课」时采用。

---

### 方案 C：保留当前三层，但小组课优先走「学号+课程」（折中）

**做法**：当存在 `group_student_ids` 时，**先**做一次「学号 + 课程」的简单查询；若有结果直接使用。若无结果，再走现有的「主查询 → course_code 回退」（例如兼容 group_id 为主、course_id 异常的老数据）。

**优点**：
- 常见情况（数据规范）一次查询即命中，和方案 A 一样简单。
- 异常/旧数据仍有多一层保护，兼容性接近当前方案。

**缺点**：
- 仍保留多层逻辑，只是调整了顺序，代码复杂度没有根本下降。

**结论**：在不想大改、又希望「大多数情况只查一次」时可用。

---

## 四、建议汇总

| 诉求 | 建议 |
|------|------|
| **当前先保证功能稳定** | 维持现有三层逻辑即可，重点确认前端小组选项始终带 `studentIds`、且与排课结果一致。 |
| **优先简单、少踩坑** | 采用 **方案 A**：小组课有 `group_student_ids` 时只做「学号 + 课程」单次查询，去掉主查询/班级/course_code 回退对小组的分支。 |
| **需要接口解耦或复用** | 采用 **方案 B**，单独提供「按学号查排课时间」接口。 |
| **少改代码、略优化性能** | 采用 **方案 C**，把「学号+课程」提到第一步，有结果就直接用。 |

整体上，**方案 A** 最符合「根据学生学号直接读取排课结果」的语义，实现和维护成本最低；若对历史数据中「仅 course_code、无 course_id」的极端情况仍有顾虑，可先采用 **方案 C**，再视数据情况逐步收敛到方案 A。
